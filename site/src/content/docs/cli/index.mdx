Run via `npx @ambystech/ambykit <command>` or install globally and use `ambykit <command>`.

## Global flags

- `--verbose` — detailed logging.
- `--dry-run` — show what would change without writing files.
- `--yes` — assume yes for prompts; skips interactive tool selection.

Output adapts to your terminal — color + glyphs when interactive, plain text when piped or under
`NO_COLOR`, ASCII fallback where glyphs are unsupported, and byte-stable `--json`.

## `ambykit init [dir]`

```text
ambykit init [dir] [--tools=claude,…] [--yes] [--dry-run]
```

Scaffold AmbyKit into a project: creates `.amby/` (constitution + `config.json`), detects installed
assistants, emits their native files, and writes the shared `AGENTS.md` (+ `CLAUDE.md` bridge for
Claude). With no `--tools` on an interactive terminal it opens a tool picker.

**Brownfield-safe.** `init` detects an existing project (a rules file, source files, or git history)
and merges rather than overwrites: existing `CLAUDE.md`/`AGENTS.md` content is preserved and only
AmbyKit's `### AmbyKit usage` section is added/updated. The file is backed up to `.amby/backups/`
first, a section you hand-edited is left untouched, and `--dry-run` previews the change.

## `ambykit add <tool…>`

```text
ambykit add <tool…> [--dry-run]
```

Add or refresh one or more targets (see [tool compatibility](/cli/compatibility/)). With no target on
a TTY it opens a multi-select picker; non-interactively it errors with the available targets.

## `ambykit sync`

```text
ambykit sync [--check] [--include-user] [--dry-run]
```

Re-emit all configured tools from the neutral source. `--check` exits non-zero if anything is out of
date (used in CI). User-level MCP files are opt-in via `--include-user`. `sync` is also the
**update path** for existing docs — it merges AmbyKit's section into each tool's rules file
non-destructively (preserve, back up, skip hand-edits), keeping your agent docs current.

## `ambykit dashboard [story-id]`

```text
ambykit dashboard [story-id] [--interactive] [--json] [--status=X] [--feature=X] [--icons=nerd|unicode|ascii]
```

Progress view over the story/task graph, computed locally from `specs/*/spec.md` + `tasks.md` (zero
model tokens). It reads every feature worktree under `.worktrees/` too, so progress made in a
worktree shows up from any checkout. `--interactive` opens a full-screen navigable view on a TTY
that updates live as files change and shows which assistant is working on which feature.

### Fleet view

While a fleet run is unfinished (`ambykit fleet` or `ambykit run`), press `l` in `--interactive` to see its
lanes live: each lane's assistant, state (always a word as well as a glyph), quiet time and directive
status, a `STALLED <n>m` label on a lane that has gone quiet past `fleet.stallMinutes` (default 15), the
run's review stage and round in the header, and any story gate waiting for you. `p` pauses, `u` continues
and `x` stops the selected lane (stop asks `y`/`n` first); `P`, `U` and `X` do the same for the whole run and
always ask. `a` approves a waiting gate, the same action as `ambykit run approve`. A pause or stop is a
directive the worker obeys at its next report. The view reads local files only, works without color and at
any width, and is not loaded outside `--interactive`. `--json --overview` carries the same data as an
optional `fleet` object while a run is unfinished.

### Icons

The dashboard uses Unicode icons by default (`⎇` for a worktree, `✸ Claude`, `◎ Codex`, …) and
ASCII tags (`wt`, `[CC] Claude`) where Unicode isn't supported. If your terminal font is a
[Nerd Font](https://www.nerdfonts.com/), you can switch the worktree tag to the git-branch icon
(`oct-git_branch`, U+F418). Agent icons stay Unicode in every mode, because older Nerd Fonts lack
the brand glyphs.

| Way | Scope |
| --- | --- |
| `ambykit dashboard --interactive --icons=nerd` | One run |
| `AMBYKIT_ICONS=nerd` environment variable | Every run where it's set |
| `"dashboard": { "icons": "nerd" }` in `.amby/config.json` | Everyone who uses the project |

The flag wins over the variable, and the variable wins over the config, so `--icons=unicode` turns Nerd
icons off for one run, and `--icons=ascii` forces ASCII tags. The config value is `nerd`, `unicode`,
`ascii` or `auto` (the default: Unicode where the terminal supports it); you edit it by hand and the
dashboard never writes it. A terminal without Unicode is always ASCII. To set the variable permanently:

```powershell
# Windows (PowerShell); open a new terminal afterwards
[Environment]::SetEnvironmentVariable("AMBYKIT_ICONS", "nerd", "User")
```

```bash
# macOS / Linux: add to ~/.zshrc or ~/.bashrc
export AMBYKIT_ICONS=nerd
```

Whether Nerd icons render depends on each person's terminal font, and `.amby/config.json` is shared
through git, so set `dashboard.icons` only when the whole team shares a font. Anyone can still override it
with the variable or the flag.

## `ambykit analyze`

```text
ambykit analyze [--json]
```

Cross-check spec ↔ plan ↔ tasks for coverage, consistency, and dependency-graph health. Read-only.

## `ambykit graph`

```text
ambykit graph [feature] [--json | --mermaid]
```

Print the story and feature dependency graph, built locally from `specs/` (no model tokens). Shows
what depends on or is blocked by what, the feature dependencies that follow from it, and any broken
references or cycles, which are listed first and make the command exit non-zero. Give a feature to see
it and its direct neighbours. `--json` is a versioned machine shape; `--mermaid` prints a flowchart.

## `ambykit check`

```text
ambykit check
```

Validate the project's AmbyKit setup and configuration.

Also reports stale worktrees and role problems in `.amby/roles/` (oversized, duplicate ids, deleted
defaults). `ambykit sync` validates roles the same way and emits one native sub-agent per role for
Claude Code, OpenCode, and Copilot.

## `ambykit restore [file]`

```text
ambykit restore [file]   # no file → list available backups
```

Recover an agent-doc file (`AGENTS.md`, `CLAUDE.md`, …) from the timestamped backup AmbyKit writes to
`.amby/backups/` before it modifies an existing file. With no argument it lists what can be restored.

## `ambykit worktree`

```text
ambykit worktree <feature>          # create .worktrees/<feature> on branch <feature>
ambykit worktree list               # feature, branch, clean/dirty/merged, path
ambykit worktree remove <feature>   # delete the working copy; branch is kept (--force if dirty)
```

Per-feature git worktrees for parallel work without checkout switching. Worktrees live at
`.worktrees/<feature>/` (gitignored); new branches start from the default branch. Enable automatic
creation from `/amby.specify` at `ambykit init` or with `"worktrees": true` in `.amby/config.json`.

## `ambykit lane`

```text
ambykit lane <feature> [--phase=N] [--lanes=N]   # one worktree per group of disjoint [P] tasks
ambykit lane list [<feature>]                    # tasks, done/total, clean/dirty/merged, drift
ambykit lane merge <feature> [<lane>]            # merge finished lanes into the feature branch
ambykit lane remove <feature> [<lane>]           # remove working copies; branches are kept (--force if dirty)
```

Parallel lanes split one phase's `[P]` tasks into isolated worktrees named
`.worktrees/<feature>.lane-<phase>-<k>`. Creation is refused when tasks share files, and needs
`"worktrees": true` in `.amby/config.json`. `merge` resolves check-off-only `tasks.md` differences
automatically and aborts on any other conflict. `ambykit analyze` also reports **lane conflicts**:
overlapping task paths in a phase where one of the tasks is `[P]`.

## `ambykit trace`

```text
ambykit trace [feature] [--json] [--gate]
```

Shows which requirements have tests, at zero model tokens and without editing anything. A test covers
a requirement when its name begins with the qualified id: `it("019:FR-004: …")` (several ids may be
listed). The report lists covered and uncovered requirements, orphans (tests citing an unknown id) and
uncited tests. `--json` prints a versioned shape; `--gate` exits 1 when a requirement is uncovered. A
requirement left untested on purpose is recorded as `uncovered: FR-### — reason` in `tests.md`.

## `ambykit migrate`

```text
ambykit migrate [feature] [--dry-run] [--diff] [--dual-write]
```

Converts the 1.x `spec.md` and `tasks.md` files of this checkout to the v2 format: story metadata moves into the spec's
frontmatter, each phase's file ownership and Verify line move into one `yaml` block, and both files gain `format: 2`. Prose and
checkboxes are never rewritten. A file that is not provably safe is left untouched and listed with the fix, every conversion is
read back before it is written, each file is written once, and a second run changes nothing. `--dry-run` writes nothing,
`--diff` prints each change, `--dual-write` keeps the 1.x lines beside the v2 data. A 1.x AmbyKit loses statuses,
dependencies, ownership and Verify results on a v2 file without an error, so upgrade your tools first.

## `ambykit edit`

```text
ambykit edit files <feature> <T###> <path…>
ambykit edit verify <feature> <phase> --result=passed|failed|unverified [--why=<text>]
ambykit edit status <feature> <US-#> <status>
```

Sets a task's files, a phase's Verify result or a story's status in the right place for the file's format, in v2 and 1.x alike,
so nobody hand-edits YAML. It changes only that one field, reads the file back and refuses (changing nothing) if anything else
would change, or on an unknown task, story or phase, an invalid status or result, or a glob path.

## `ambykit activity`

```text
ambykit activity <feature> --agent=<tool-id> --phase=<phase> [--task=T###] [--lane=<lane>] [--state=<state>] [--run=<id>]
```

Records that an assistant started a phase on a feature, for the dashboard's agent presence. The
phase prompts run it for you; it writes `.amby/activity/<feature>.<agent>.json` (git-ignored) and
never fails: problems are warnings and it always exits 0. For a fleet lane, `--lane`, `--state`
(`working`, `waiting`, `blocked`, `paused` or `done`) and `--run` add the lane to the file name and
the fleet fields to the marker; without them the marker is unchanged.

## `ambykit mcp`

```text
ambykit mcp
```

Serves AmbyKit's state tools to an assistant over MCP on stdio: the next unblocked task, a story's
blockers, a validated tick, a report that returns a pause or stop directive, file claims and notes.
The assistant starts it; you do not run it by hand. It is opt-in: set `"mcp": { "enabled": true }` in
`.amby/config.json`, then `ambykit sync` writes the verified assistants' MCP config. Every phase still
works from files when the server is absent.

## `ambykit directive`

```text
ambykit directive <feature> <lane> pause|resume|stop [--run=<id>]
```

Tells a fleet lane to pause, resume or stop. The worker finishes its current task and obeys at its next
report. An unknown lane is refused by name.

## `ambykit fleet`

The helper `/amby.run` and its workers call, so every change to a run goes through one validated path. It
keeps no state of its own: runs, claims, notes and directives are the fleet state under `.amby/fleet/<run>/`,
and stall detection is the same one the dashboard uses.

```text
ambykit fleet start 019 [--new]          # create run 019-...N; refuses when one is unfinished unless --new
ambykit fleet status 019 [--run=<id>] [--json] [--rebuild]
ambykit fleet update 019 --worker-start=lane-1-1 --assistant=claude --tasks=T001,T002
ambykit fleet update 019 --stage=qa | --phase=2 | --round=2 | --decision="<text>" | --done
ambykit fleet update 019 --pause[=<lane>] | --resume[=<lane>] | --stop[=<lane>]
ambykit fleet update 019 --overlap=squad --lanes=a,b --shared=<path> --writer=<path>:<lane> --order=a,b
ambykit fleet claim 019 T012 src/a.ts [--worker=<id>]   # refused, naming the owner, when held
ambykit fleet release 019 T012
ambykit fleet note 019 T012 --files=src/a.ts "one-line note"
ambykit fleet directive 019 lane-1-1     # prints continue, pause or stop
```

`start` creates nothing for a feature that is already done or whose spec, plan or tasks are missing or draft.
`status` prints the run, the next phase, each lane (state, idle time, directive, restarts left), free slots
under `fleet.concurrency`, and warnings: damaged state, a checked task that still holds claims, a lane edit
with no claim. `--rebuild` rewrites a missing or corrupt `run.json` from `tasks.md` and never touches checked
tasks. `--worker-start` is refused when no slot is free; `--restart` is refused after `fleet.restartLimit`
restarts, pausing the lane and asking a person. `--round` prints `retry` or `escalate` and, on `escalate`,
waits for a decision. Pause, resume and stop go through the same writer as `ambykit directive`.

## `ambykit run` (experimental)

Run a feature's prepared lanes headless, one assistant per lane. Experimental in 1.6. Nothing launches without
`--yes`, and only a verified runner is ever launched.

```text
ambykit run 028                         # print the exact command per lane; launch nothing
ambykit run 028 --yes                   # print, then launch and supervise
ambykit run 028 --emit-script           # write launch.sh and launch.ps1; launch nothing
ambykit run --continue-run=<run> --yes  # continue a stopped or interrupted run
ambykit run --runners                   # which headless runners are verified
ambykit run approve|reject <run>        # a story checkpoint
```

Name several features (`ambykit run 030 031 032`) or pass `--all-ready` to run them as **one fleet** (experimental): lanes
are planned across features by file ownership and feature dependencies, a feature waits for the one it depends on
(once that feature's lanes are merged into its branch), features that share a file run one after the other, caps and
budgets apply to the whole fleet, and a failing lane pauses only its feature and what depends on it.
`ambykit run --continue-fleet=<fleet>` resumes a stopped fleet, `ambykit run pause|stop|resume <fleet>` steers it, and
`ambykit fleet fleets` shows every feature's lanes. A single feature is the run below, unchanged.

Prepare lanes first with `ambykit lane`. The run restarts stalled lanes, reviews each finished lane (QA, then the
architect) before merging it, merges one at a time, stops at story checkpoints, and enforces wall-clock and task
budgets. State is `.amby/fleet/<run>/`, shared with `/amby.run`. See the CLI reference for every flag.

## `ambykit update`

```text
ambykit update
```

Update the AmbyKit CLI to the latest published version when it's behind, then — on a re-run once
current — refresh this project's tool prompts. When outdated it upgrades the CLI and asks you to
**re-run** `ambykit update` to refresh prompts under the new version; if it can't self-update (e.g. an
`npx` run or a permissions error) it prints the exact `npm install -g` command.
